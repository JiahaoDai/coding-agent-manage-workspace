# Coding Agent 管理界面 — v1 规格说明

> 来源：`docs/design.md`（草稿，工作名 coding-agent-dashboard，待命名）
> 日期：2026-08-17

## 问题陈述

开发者同时在本地使用多个 coding-agent（首批：Claude Code、OpenCode、Pi），每个 agent 各有自己的 CLI、会话存储与流式输出。要同时使用它们，就得在多个终端之间来回切换，并记住每段对话存在哪里。开发者需要一个统一的本地界面：能创建会话、与任意 agent 进行多轮对话（并发、流式、可见工具调用与思考过程），并且——因为 agent 会真实执行命令、修改文件——能在界面上批准或拒绝每一个危险操作。该界面不应重复存储各 agent 原生的消息正文。

## 解决方案

一个本地单用户 Web 应用：React + Vite 客户端（纯展示）通过 SSE（下行，单条复用流）与 REST POST（上行）与 Node 后端通信。后端是 agent SDK、SQLite、文件系统的唯一调用方。每个 agent 通过官方 SDK 以无头方式驱动，统一收纳在同一个**适配器接口**之后；新增一个 agent 只需新增一个 adapter。后端仅在 SQLite 保存会话元数据（界面自有的 session id、所属 agent、该 agent 的原生 session id、展示名称、工作目录、状态、时间戳）——消息正文始终从 agent 原生存储读取。agent 触达系统层面的操作会在界面以权限请求的形式弹出，由用户同意或拒绝。

## 用户故事

1. 作为一个开发者，我希望通过选择项目目录来创建新会话，以便 agent 在正确的工作目录中运行。
2. 作为一个开发者，我希望选择会话使用哪个 coding-agent（Claude Code / OpenCode / Pi），以便为任务挑选合适的 agent。
3. 作为一个开发者，我希望给会话指定展示名称，以便在列表中区分不同会话。
4. 作为一个开发者，我希望应用能检测所选目录与 agent 下已有的原生会话，以便接续之前的工作而非总是从头开始。
5. 作为一个开发者，我希望在「续用已有原生会话」和「新建会话」之间做选择，以便不丢失先前的对话上下文。
6. 作为一个开发者，我希望续用流程能基于原生 summary 或首条提示预填名称，以便我修改而非重打。
7. 作为一个开发者，我希望在会话中发消息并收到流式回复，以便实时与 agent 对话。
8. 作为一个开发者，我希望看到 agent 回复时文本增量输出，以便无需等整轮结束即可跟上进度。
9. 作为一个开发者，我希望看到 agent 的工具调用（命令、文件读写）及其参数，以便理解 agent 在做什么。
10. 作为一个开发者，我希望工具调用默认折叠展示，以便冗长的工具输出不扰乱对话。
11. 作为一个开发者，我希望看到 agent 的思考过程，以便理解其推理。
12. 作为一个开发者，我希望思考输出默认折叠，以便不需要时它不碍事。
13. 作为一个开发者，我希望一轮结束后会话回到空闲/已完成状态，以便知道它已准备好接收下一条消息。
14. 作为一个开发者，我希望并发运行多个会话（可能跨不同 agent），以便并行处理多项任务。
15. 作为一个开发者，我希望每个运行中的会话状态实时可见，以便一眼看出哪些在运行、哪些已完成或失败。
16. 作为一个开发者，我希望会话列表按 agent 分组或过滤，以便找到特定 agent 的会话。
17. 作为一个开发者，我希望按状态过滤会话，以便聚焦运行中或已完成的会话。
18. 作为一个开发者，我希望按关键字搜索会话，以便通过名称或目录定位某个会话。
19. 作为一个开发者，我希望列表中每个会话显示状态徽标（running / completed / error / cancelled），以便快速判断状态。
20. 作为一个开发者，我希望列表显示会话的目录与最后修改时间，以便在众多会话中自我定位。
21. 作为一个开发者，我希望软删除会话，使其从界面消失但不破坏 agent 的原生会话。
22. 作为一个开发者，我希望已删除的会话能从 agent 原生存储重新导入，以便软删除可恢复。
23. 作为一个开发者，我希望 agent 的工具操作（跑命令、改文件）需要我的确认，以便危险操作不会静默发生。
24. 作为一个开发者，我希望权限请求展示要调用的工具及其参数，以便做出知情的 allow/deny 决定。
25. 作为一个开发者，我希望从界面允许或拒绝权限请求，以便持续掌控 agent 的操作。
26. 作为一个开发者，我希望允许时 agent 继续、拒绝时告知它已被拒绝，以便审批闭环真正生效。
27. 作为一个开发者，我希望并发运行会话的权限请求各自路由到自己的窗口，以便审批绝不串台。
28. 作为一个开发者，我希望从应用内文件树选择项目目录，以便不必手打绝对路径。
29. 作为一个开发者，我希望文件树根目录限定在可配置范围（默认家目录），以便应用不爬取整个文件系统。
30. 作为一个开发者，我希望应用是本地单用户的，以便无需账号或托管服务器。
31. 作为一个开发者，我希望刷新页面或断连后 UI 能恢复会话列表与状态，以便瞬时断连不丢失我的视图。
32. 作为一个开发者，我希望消息历史在展示时从 agent 原生存储读取，以便应用永不存储重复的消息正文。

## 实现决策

- **三模块单仓**：一个仓库分为 client（React + Vite + TypeScript）、server（Node + TypeScript）、shared（前后端共用的类型契约与适配器接口）。这是本地工具，刻意不用 monorepo 工具。
- **适配器接口是唯一 seam**：每个 agent 由一个 adapter 包装，实现 common interface（由 shared 定义）。该接口至少需暴露：按工作目录创建/打开会话、列出某目录的原生会话、读取会话消息、流式推送 prompt 事件、注册权限钩子。精确方法签名是实现的第一个交付物，在写任何 agent adapter 之前先在 shared 中约定。
- **agents 与 SDK**：Claude Code 用 `@anthropic-ai/claude-agent-sdk`，OpenCode 用 `@opencode-ai/sdk`，Pi 用 `@earendil-works/pi-coding-agent`。每个 adapter 是 agent 特有行为的唯一所在。
- **后端是唯一权威**：唯一调用 agent SDK、唯一读写 SQLite、唯一访问文件系统（文件树）。客户端不直接接触任何这些。
- **仅存元数据**：SQLite 一张 session 表：`session_id`（UUID 主键，界面自有 id）、`coding_agent`、`real_session_id`（agent 原生 session id）、`name`、`cwd`（绝对路径）、`status`、`create_time`、`modify_time`。消息正文永不入库，用 `real_session_id` 从原生存储读取。索引 `(coding_agent, status, cwd)` 支撑过滤、状态分组与搜索。
- **会话状态取值**：`running` / `completed` / `error` / `cancelled`。adapter 监听 agent 生命周期事件实时驱动状态迁移。
- **软删除即物理删行**：删除只删 SQLite 行、保留 agent 原生 session，故可重新导入。不设独立「已删除」状态。
- **并发靠隔离子进程**：每个运行中的会话是独立无头子进程，天然支持并行与独立流式。
- **通信协议**：下行（server → client）为单条复用 SSE 流，每条事件带 `session_id`，客户端按 id 分发；上行（client → server）走 REST POST（发消息、答权限、增删查）。事件类型在 shared 定义一次，至少含：会话创建、文本增量、工具调用开始/结束（名称 + 参数）、思考增量、状态变更、权限请求、权限响应、会话移除、错误。依赖 `EventSource` 自动重连；断流/刷新后从 SQLite（唯一事实源）重读并重新订阅。
- **交互式权限确认**：后端以 `permissionMode: 'default'` 启动 agent，绝不用 `bypassPermissions` / `acceptEdits`。Claude Code 用 `canUseTool` 钩子（已核实，含 `AskUserQuestion` 澄清也走此回调）。请求（工具名 + 入参）经 SSE 推给客户端，用户 allow/deny 经 REST POST 回传，钩子返回相应 allow/deny。OpenCode 的 `permission` 事件与 Pi 的审批流程存在，但精确 approve/deny 回传形状未核实——需在对应 adapter 声称支持权限前逐个确认。对无法实时权限的 agent，降级为每 agent 固定权限模式。
- **目录选择用文件树**：后端读文件系统并渲染树，根目录限定在可配置范围（默认家目录），既避免浏览器直接拿绝对路径，也避免全盘遍历。
- **创建流程**：选目录 → 选 agent → 后端查该 agent 原生存储中该目录已有会话，若有则提供「续已有」vs「新建」→ 命名（续已有时预填）→ 后端创建/打开会话、写 session 行、返回前端。

## 测试决策

- **单一 seam：适配器接口**。测试永不启动真实 agent。注入 in-process 的 fake adapter（实现 shared 接口、发出脚本化事件、记录收到的调用），通过服务端公开的 REST + SSE 面，配合临时 SQLite 数据库驱动。
- **好测试的标准**：只断言外部可观察行为——SSE 流出的消息事件、客户端可见的状态迁移、会话列表内容与过滤、权限请求的 allow/deny 往返、删除只删界面记录且不调用 adapter 删原生会话。绝不断言内部接线、方法调用次数、或产生结果的代码路径。
- **被测模块**：服务端会话生命周期（创建/续用/命名/删除）、SSE 扇出（事件按 `session_id` 正确打标）、权限往返、并发会话隔离、列表/过滤/搜索行为。shared 中的适配器接口契约是 fake adapter 必须满足的边界。
- **先例**：无——这是全新仓库，这些测试将确立本仓库的模式。fake adapter 会成为后续每个服务端特性都复用的固定装置。

## 不在范围内

- 中断/取消运行中的 agent（统一取消入口）——留 v2。
- 创建时续用之外的统一「恢复/继续历史会话」入口——留 v2。
- 文件 diff 可视化——留 v2。
- 创建后的会话重命名、自定义标签——留 v2。
- 跨 agent 交接（上下文迁移）——留 v2。
- 桌面壳（Tauri，原生目录选择、系统托盘）——留 v2。
- 核实并加固 OpenCode / Pi 的权限 approve/deny 形状——是各自 adapter 的前置条件，但不属于本 spec 的构建范围，已标记给实现 agent 确认。

## 补充说明

- 本特性的唯一事实源是设计文档，含完整架构、数据模型、决策表与生命周期流程；本 spec 是对其的浓缩。
- 实现 agent 应解决或标记的未决事项：包/应用目录名；删除「运行中」会话时是否顺带终止后端子进程；文件树根目录默认值与配置方式；续用会话时 name 的预填来源。
- 应用设计为本地单用户；无认证、无多租户、无远程托管。
